# Loki Chunk, Block & Log Entry Hierarchy : Complete Understanding Guide 📊

---

## 1. One-Sentence Answer

**In Grafana Loki, individual log lines are packed into compressed "blocks," and multiple blocks — plus metadata and a lookup index — are packed together into a single "chunk," which is the actual unit written to object storage.**

---

## 2. Analogy Section 📚

Think of it like writing and publishing a **book**.

```
╔══════════════════════════════════════════════════════════╗
║                     📖 THE CHUNK (Book)                    ║
║  ┌────────────────────────────────────────────────────┐  ║
║  │  📑 BLOCK 1 (Chapter/Paragraph batch)                │  ║
║  │   📝 log-1  📝 log-2  📝 log-3   (sentences)         │  ║
║  └────────────────────────────────────────────────────┘  ║
║  ┌────────────────────────────────────────────────────┐  ║
║  │  📑 BLOCK 2 (Chapter/Paragraph batch)                │  ║
║  │   📝 log-4  📝 log-5                                 │  ║
║  └────────────────────────────────────────────────────┘  ║
║              ...                                          ║
║  ┌────────────────────────────────────────────────────┐  ║
║  │  🗂️ #blocks index (Table of Contents)                │  ║
║  │  🏷️ structuredMetadata (shared label glossary)       │  ║
║  └────────────────────────────────────────────────────┘  ║
╚══════════════════════════════════════════════════════════╝
```

1. 📝 A **log line** is one sentence — a timestamp + content + labels.
2. 📑 Loki groups sentences from the same stream/time-window into a **block** — like a paragraph, compressed as one unit.
3. 📖 Many blocks get bound together into a **chunk** — the whole book, with a table of contents (`#blocks` offsets) and a shared glossary (`structuredMetadata`) instead of repeating label info per sentence.
4. 🗄️ The finished book (**chunk**) is what actually gets shelved in object storage (S3/GCS/Azure Blob).

## 3. Complete Data/Process Flow

### STEP 1 — Log lines arrive 📝

```
┌──────────────────────────────────────────────┐
│  📝 LOG LINE                                   │
│  ts: <timestamp>                              │
│  content: <log text>                          │
│  labels: <label set, e.g. {app="foo"}>        │
└──────────────────────────────────────────────┘
```
💡 **Key insight:** Every log line always carries three things — when it happened, what it says, and which label set (stream) it belongs to.

---

### STEP 2 — Grouping into a Block 📑

```
┌──────────────────────────────────────────────┐
│  📑 BLOCK (uncompressed view)                  │
│  | ts | len | log-1 bytes | symbols... |      │
│  | ts | len | log-2 bytes | symbols... |      │
│  | ts | len | log-3 bytes | symbols... |      │
│  ...                                          │
│  → then compressed as ONE unit                │
└──────────────────────────────────────────────┘
```
💡 **Key insight:** Compression happens **at the block level**, not per log line. "Symbols" are references into the chunk's shared metadata rather than repeated label text.

---

### STEP 3 — Packing Blocks into a Chunk 🗄️

```
┌──────────────────────────────────────────────────────────┐
│  🗄️ CHUNK (binary layout)                                  │
│  | block-1 bytes | checksum | block-2 bytes | checksum |  │
│  | ... | block-n bytes | checksum |                       │
│  ---------------------------------------------------------│
│  #blocks section → offsets/lengths of each block          │
└──────────────────────────────────────────────────────────┘
```
💡 **Key insight:** The chunk stores each compressed block **plus a per-block checksum**, then an index (`#blocks`) so Loki knows exactly where each block starts/ends without decompressing everything.

---

### STEP 4 — Chunk Header + Metadata 🏷️

```
┌──────────────────────────────────────────────┐
│  🏷️ CHUNK HEADER / METADATA                    │
│  magic number | version | encoding            │
│  label metadata                               │
│  structuredMetadata (shared, not per-line)    │
└──────────────────────────────────────────────┘
```
💡 **Key insight:** Label metadata is stored **once per chunk**, not once per log line — this is a core part of how Loki keeps storage compact.

---

### STEP 5 — Chunk written to storage; index points to it 📤

```
┌──────────────────────────────────────────────┐
│  📤 OBJECT STORAGE (S3 / GCS / Azure Blob)     │
│      stores → 🗄️ CHUNK                         │
│                                                │
│  🔍 INDEX: {label set + time range} → chunk ID │
└──────────────────────────────────────────────┘
```
💡 **Key insight:** The **index never stores logs** — it only points to which chunk(s) to look inside for a given label set + time range. The chunk is the real payload.

## 4. Deep Dive Sections

### 📝 Log Entry (Log Line)

**What it is:** The smallest unit — one line of log output.
**What it contains:** `ts` (timestamp), `len` (length), the log text bytes, and `symbols` (references to shared metadata).
**Why it matters:** It's the atomic piece of data everything else is built from.

```
Example A                         Example B
┌───────────────────┐             ┌───────────────────┐
│ 📝 ts: 12:00:01     │             │ 📝 ts: 12:00:02     │
│ log: "GET /home"   │             │ log: "POST /login" │
│ labels: {app="web"}│             │ labels: {app="web"}│
└───────────────────┘             └───────────────────┘
```
Same label set (`app="web"`) → both entries land in the **same block/stream**, just different timestamps/content.

---

### 📑 Block

**What it is:** A batch of log entries from the same stream and time window.
**What it contains:** A repeating list of `| ts | len | log bytes | symbols |` rows, compressed as a single unit.
**Why it matters:** This is where compression actually happens — grouping similar, time-adjacent entries together compresses far better than compressing lines individually.

```
Example A (same stream)           Example B (different stream)
┌─────────────────────┐           ┌─────────────────────┐
│ 📑 BLOCK             │           │ 📑 BLOCK             │
│ labels: {app="web"}  │           │ labels: {app="db"}   │
│ 3 entries, compressed│           │ 5 entries, compressed│
└─────────────────────┘           └─────────────────────┘
```
Different label sets → Loki keeps them in **separate blocks** (and typically separate streams entirely), since blocks are organized per stream + time range.

---

### 🗄️ Chunk

**What it is:** The top-level, umbrella container — the actual object written to storage.
**What it contains:** Multiple compressed blocks + per-block checksums + a `#blocks` offset index + header (magic number, version, encoding) + shared `structuredMetadata`.
**Why it matters:** It's the unit of storage and retrieval — Loki fetches whole chunks (then seeks into the relevant block) rather than fetching individual log lines directly.

```
Example A (few blocks)            Example B (many blocks)
┌─────────────────────┐           ┌─────────────────────┐
│ 🗄️ CHUNK             │           │ 🗄️ CHUNK             │
│ block-1, block-2     │           │ block-1 ... block-9  │
│ small #blocks index  │           │ larger #blocks index │
└─────────────────────┘           └─────────────────────┘
```
More log volume for a stream/time-window → **more blocks packed into the chunk**, with a correspondingly larger offset index — the chunk's own structure doesn't change, just how much it holds.

---

### 🔍 Index

**What it is:** The lookup layer, separate from chunks.
**What it contains:** Mappings from `{label set + time range}` → chunk ID(s).
**Why it matters:** Lets Loki find the right chunk(s) fast without scanning all storage.

## 5. Full Lifecycle Diagram 🔁

```
1️⃣ Log line generated
        ▼
2️⃣ 📝 ts + content + labels attached
        ▼
3️⃣ Grouped with same-stream, same-time-window log lines
        ▼
4️⃣ 📑 Packed into a BLOCK → compressed as one unit
        ▼
5️⃣ Repeat 2️⃣–4️⃣ → multiple blocks accumulate
        ▼
6️⃣ 🗄️ Blocks + checksums + #blocks index + header +
      structuredMetadata → assembled into a CHUNK
        ▼
7️⃣ 📤 CHUNK written to object storage;
      🔍 INDEX updated to point {labels+time} → chunk ID
```

## 6. Comparison Example ⚖️

| Scenario | Same labels, same time window | Different labels |
|---|---|---|
| Log lines | `{app="web"}` × 3 | `{app="web"}` × 2, `{app="db"}` × 1 |
| Grouping | All 3 → **one block** | Split across **two blocks** (per stream) |
| Chunk effect | One block added to chunk | Two separate blocks added to chunk |
| Metadata | One shared label entry in `structuredMetadata` | Two shared label entries, one per stream |

**Cause → effect:** Changing the **label set** of incoming log lines changes which **stream** (and therefore which **block**) they're grouped into — it does not change the chunk format itself, only how many distinct blocks the chunk ends up holding.

## 8. Key Takeaways ✅

**Containment order**
- ✅ Log entries go **into** blocks.
- ✅ Blocks go **into** chunks.
- ✅ The **chunk** is the outer/umbrella structure — not the reverse.

**Compression & efficiency**
- ✅ Compression happens **per block**, not per log line.
- ✅ Label/metadata info is stored **once per chunk** (`structuredMetadata`), and log entries reference it via `symbols` instead of repeating it.

**Storage & lookup**
- ✅ The **chunk** is the actual object written to S3/GCS/Azure Blob.
- ✅ The **index** never holds log data — it only maps `{label set + time range}` to the relevant chunk ID(s).

**One-line summary:**
📝 Log line → 📑 Block (grouped + compressed) → 🗄️ Chunk (blocks + metadata + index) → 📤 Object storage (looked up via 🔍 Index)

## 9. Memory Trick 🧠

> **"Sentences make paragraphs, paragraphs make a book."**
> 📝 Log line = sentence · 📑 Block = paragraph (compressed) · 🗄️ Chunk = the whole book (with its own table of contents and glossary)

If you're ever unsure "does the log go into the chunk or the block?" — remember: **you can't skip the paragraph to bind loose sentences straight into a book.** Logs → Blocks → Chunks, always in that order.

---

### Plain-language recap

The original explanation was answering the question "does a log go into a chunk or a chunk go into a block?" The answer: it's **logs → blocks → chunks**. Individual log lines (timestamp + content + labels) are grouped by stream and time window into **blocks**, which are compressed as a unit. Multiple compressed blocks, together with checksums, an offset index (`#blocks`), a header (magic number/version/encoding), and shared label metadata (`structuredMetadata`), are packed into a single **chunk**. The chunk — not the block, and not the raw log lines — is the actual object Loki writes to object storage (S3/GCS/Azure Blob). The separate **index** doesn't store any logs at all; it just maps a label set and time range to the chunk ID(s) Loki should look inside.
