# Grafana Loki Components : Complete Understanding Guide 📊

---

## One-Sentence Answer

**Loki is a modular logging system where specialized components (Distributor, Ingester, Querier, etc.) each handle one job in the write path (ingesting logs) or read path (querying logs), and they can run together or scaled independently.**

---

## Analogy Section 🏤

Think of Loki like a **postal sorting depot and archive**.

```
╔══════════════════════════════════════════════════════════════╗
║              📬 THE LOKI POST OFFICE ANALOGY                  ║
║                                                                ║
║   ✉️ Incoming Mail (logs)                                     ║
║        │                                                       ║
║        ▼                                                       ║
║   🧑‍💼 Front Desk Clerk (Distributor)                          ║
║   - checks address format is valid                            ║
║   - sorts envelopes alphabetically                            ║
║   - sends copies to 3 storage clerks                          ║
║        │                                                       ║
║        ▼                                                       ║
║   🗄️ Storage Clerks (Ingesters)                                ║
║   - hold mail in an in-tray (memory/chunks)                   ║
║   - file it into the archive room (long-term storage)         ║
║        │                                                       ║
║        ▼                                                       ║
║   🏛️ Archive Room (Object Storage: S3/GCS/Azure)               ║
║                                                                ║
║   🔍 When someone wants mail back:                             ║
║   📞 Reception (Query Frontend) → 🎟️ Ticket Queue              ║
║   (Query Scheduler) → 🕵️ Investigator (Querier) → 📇 Index    ║
║   Card Catalog (Index Gateway) → 🏛️ Archive Room               ║
╚══════════════════════════════════════════════════════════════╝
```

**Process:**
1. Mail (logs) arrives at the front desk (Distributor), gets validated and sorted.
2. Copies go to 3 storage clerks (Ingesters) for safety (replication factor).
3. Clerks keep mail in an in-tray (memory) then file it away (object storage) periodically.
4. When someone requests old mail, the request goes through reception (Query Frontend), waits in a ticket queue (Query Scheduler), and an investigator (Querier) fetches it — checking the card catalog (Index Gateway) to know exactly where it's filed.

## Complete Data/Process Flow

### STEP 1 — Write Request Arrives at Distributor

```
┌─────────────────────────────────────────────────────────┐
│  📥 STEP 1: Incoming Push Request                        │
│                                                            │
│  Client sends stream:                                     │
│    {foo="bar", bazz="buzz"}  ──▶  🧑‍💼 Distributor         │
│                                                            │
│  Checks performed:                                         │
│   ✔️ Valid Prometheus-style labels                        │
│   ✔️ Timestamp not too old/new                            │
│   ✔️ Log line not too long                                │
│                                                            │
│  💡 Distributor is STATELESS → easy to scale horizontally │
└─────────────────────────────────────────────────────────┘
```

### STEP 2 — Preprocessing (Label Normalization)

```
┌─────────────────────────────────────────────────────────┐
│  🔤 STEP 2: Normalize Labels                              │
│                                                            │
│   Input:  {foo="bar", bazz="buzz"}                        │
│   Output: {bazz="buzz", foo="bar"}   (sorted)              │
│                                                            │
│  💡 Sorting makes labels deterministic → enables          │
│     caching & consistent hashing later                     │
└─────────────────────────────────────────────────────────┘
```

### STEP 3 — Rate Limiting (Global, Per-Tenant)

```
┌─────────────────────────────────────────────────────────┐
│  🚦 STEP 3: Rate Limiting Example                         │
│                                                            │
│  Tenant A limit = 10MB/s                                  │
│                                                            │
│   10 distributors  → 10MB / 10 = 1MB/s per distributor    │
│   +10 new distributors join (20 total)                    │
│   20 distributors  → 10MB / 20 = 500KB/s per distributor  │
│                                                            │
│  💡 Global limit ÷ current distributor count =            │
│     automatically-adjusting per-distributor limit          │
└─────────────────────────────────────────────────────────┘
```

### STEP 4 — Hashing & Replication to Ingesters

```
┌─────────────────────────────────────────────────────────┐
│  🔗 STEP 4: Consistent Hashing via the Ring               │
│                                                            │
│  Ring tokens (example):  0 ── 25 ── 50                    │
│  Stream hash = 3                                           │
│  → smallest token > 3 is 25                                │
│  → owning Ingester of token 25 gets the write              │
│    (responsible for hash range 1–25)                       │
│                                                            │
│  Replication Factor (RF) = 3                                │
│   Write sent to 3 Ingesters in parallel                    │
│   Quorum needed = floor(3/2)+1 = 2 successful writes       │
│                                                            │
│  💡 2 of 3 must succeed, or the write is retried/fails     │
└─────────────────────────────────────────────────────────┘
```

### STEP 5 — Ingester Buffers & Flushes Chunks

```
┌─────────────────────────────────────────────────────────┐
│  🗄️ STEP 5: Chunk Lifecycle inside Ingester                │
│                                                            │
│  Writable Chunk (in memory) ──▶ becomes read-only when:    │
│    • capacity reached (configurable)                       │
│    • too much time passed w/o update                       │
│    • a flush occurs                                        │
│                                                            │
│  On flush → chunk hashed by (tenant + labels + contents)   │
│           → sent to Object Storage (S3/GCS/Azure)          │
│                                                            │
│  💡 Write-Ahead Log (WAL) + Replication Factor together    │
│     protect against data loss if an Ingester crashes        │
└─────────────────────────────────────────────────────────┘
```

### STEP 6 — Query Path: Frontend → Scheduler → Querier

```
┌─────────────────────────────────────────────────────────┐
│  🔍 STEP 6: Read Path                                      │
│                                                            │
│  Client Query                                              │
│     │                                                       │
│     ▼                                                       │
│  📞 Query Frontend  (splits large queries, caches results)  │
│     │                                                       │
│     ▼                                                       │
│  🎟️ Query Scheduler (per-tenant FIFO queue, optional)       │
│     │                                                       │
│     ▼                                                       │
│  🕵️ Querier (pulls job, executes, returns result)           │
│     │                    │                                  │
│     ▼                    ▼                                  │
│  In-memory data     📇 Index Gateway → chunk refs           │
│  from Ingesters         → 🏛️ Object Storage                 │
│                                                            │
│  💡 Querier deduplicates results matching identical         │
│     nanosecond timestamp + labels + log message              │
└─────────────────────────────────────────────────────────┘
```

### STEP 7 — Background Maintenance (Compactor, Ruler, Bloom*)

```
┌─────────────────────────────────────────────────────────┐
│  🧹 STEP 7: Background Jobs                                │
│                                                            │
│  🗜️ Compactor: merges many small per-day index files       │
│     into ONE file per day/tenant + handles retention        │
│                                                            │
│  ⏰ Ruler: evaluates alert/recording rules on a schedule     │
│                                                            │
│  🌸 Bloom Planner → 🌸 Bloom Builder → 🌸 Bloom Gateway      │
│     (Experimental) build/query bloom filters to skip         │
│     chunks that don't match a filter expression               │
│                                                            │
│  💡 These run continuously in the background, independent   │
│     of any single read/write request                         │
└─────────────────────────────────────────────────────────┘
```

## Deep Dive Sections

### 🧑‍💼 Distributor

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: First stop on the write path              │
│  CONTAINS:   Validation logic, label sorter,             │
│              rate limiter, ring-lookup client            │
│  WHY IT MATTERS: Stateless → scales freely, shields      │
│    Ingesters from bad/overloaded traffic (DoS protection)│
│                                                            │
│  Example A: 10 distributors, Tenant A = 10MB/s            │
│             → 1MB/s per distributor                        │
│  Example B: 20 distributors, Tenant A = 10MB/s             │
│             → 500KB/s per distributor                       │
│  (Same tenant limit, different distributor count           │
│   → different per-node throttling)                          │
└───────────────────────────────────────────────────────┘
```

### 🗄️ Ingester

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Persists data, ships to long-term storage,  │
│              serves recent in-memory data for reads       │
│  CONTAINS:   Lifecycler (ring state), in-memory chunks,   │
│              Write-Ahead Log                               │
│  WHY IT MATTERS: The most critical component on the        │
│    write path — data loss risk if it crashes unflushed      │
│                                                            │
│  Example A (in-order mode): logs sent 10:00, 10:01, 10:02  │
│             → all accepted, ascending order                 │
│  Example B (out-of-order default): logs sent 10:02, 10:00  │
│             → BOTH accepted (Loki defaults to allow          │
│               out-of-order writes)                           │
│  Example C (duplicate same ns timestamp + same text)        │
│             → line IGNORED as exact duplicate                │
│  Example D (same ns timestamp, different text)               │
│             → BOTH lines accepted                             │
└───────────────────────────────────────────────────────┘
```

**States an Ingester can be in:**

```
┌────────────┬──────────────────────────────────────────┐
│ PENDING    │ waiting for handoff (legacy/deprecated)   │
│ JOINING    │ inserting tokens, can receive writes      │
│ ACTIVE     │ fully up — receives read + write requests │
│ LEAVING    │ shutting down — can still serve reads     │
│ UNHEALTHY  │ missed heartbeat, marked by Distributor   │
└────────────┴──────────────────────────────────────────┘
```

### 📞 Query Frontend

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Optional API-facing accelerator for reads    │
│  CONTAINS:   Internal query queue, splitter, result cache  │
│  WHY IT MATTERS: Prevents OOM by splitting huge queries,   │
│    parallelizes work across Queriers, caches results        │
│                                                            │
│  Example A: Metric query result cache                      │
│    → caches ACTUAL numeric results for reuse                │
│  Example B: Log query cache ("negative cache")              │
│    → caches EMPTY results for time ranges, not the logs      │
│    themselves (log queries return too much raw data to        │
│    cache directly)                                            │
└───────────────────────────────────────────────────────┘
```

### 🎟️ Query Scheduler

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Optional, more advanced queue than the        │
│              basic one built into Query Frontend            │
│  CONTAINS:   Per-tenant in-memory FIFO queues                │
│  WHY IT MATTERS: Guarantees query fairness across tenants   │
│    — one tenant can't starve another's queries                │
│                                                            │
│  Example A: Without Scheduler → Frontend does simple queue  │
│  Example B: With Scheduler → dedicated per-tenant queues,   │
│             Queriers pull jobs via -querier.scheduler-address│
└───────────────────────────────────────────────────────┘
```

### 🕵️ Querier

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Executes LogQL queries                        │
│  CONTAINS:   Logic to query Ingesters (recent/in-memory)    │
│              AND long-term storage, then deduplicate         │
│  WHY IT MATTERS: Bridges "hot" recent data with "cold"       │
│    archived data into one unified answer                      │
│                                                            │
│  Example A: Query hits 3 replicated Ingesters                │
│             → same log line comes back 3x                     │
│             → Querier dedups by (timestamp+labels+message)    │
│  Example B: Query time range fully in object storage          │
│             → Querier skips Ingesters, reads Index Gateway     │
│             + backend store only                                │
└───────────────────────────────────────────────────────┘
```

### 📇 Index Gateway

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Serves metadata/index lookups                 │
│  CONTAINS:   Index for chunk references, log volume data    │
│  WHY IT MATTERS: Tells Queriers WHICH chunks to fetch,       │
│    tells Query Frontend how to shard queries                  │
│                                                            │
│  Example A: Simple mode → 1 instance serves ALL tenants      │
│  Example B: Ring mode → instances shard tenants via a         │
│             consistent hash ring (scales horizontally)         │
└───────────────────────────────────────────────────────┘
```

### 🗜️ Compactor

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Index file housekeeper                         │
│  CONTAINS:   Logic to download, merge, re-upload index files │
│  WHY IT MATTERS: Many small per-ingester index files →       │
│    ONE efficient file per day/tenant; also handles retention  │
│    & deletion                                                  │
│                                                            │
│  Example A: 10 Ingesters each ship an index file/day          │
│             → Compactor merges into 1 file/day/tenant          │
│  Example B: Retention policy set to 30 days                    │
│             → Compactor deletes chunks/index older than that   │
└───────────────────────────────────────────────────────┘
```

### ⏰ Ruler

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Alert / recording rule evaluator               │
│  CONTAINS:   Rule configs (from object storage or local fs)  │
│  WHY IT MATTERS: Turns log queries into Prometheus-style      │
│    alerts automatically on a schedule                          │
│                                                            │
│  Example A: Local evaluation → Ruler executes rule itself      │
│  Example B: Remote rule evaluation → delegated to Query         │
│             Frontend to gain splitting/caching benefits          │
└───────────────────────────────────────────────────────┘
```

### 🐝 Pattern Ingester

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Optional log-pattern detector (disabled       │
│              by default)                                     │
│  CONTAINS:   Drain algorithm output → patterns as             │
│              (number, string, series identifier)               │
│  WHY IT MATTERS: Powers the "Patterns" tab in Grafana          │
│    Logs Drilldown, letting users spot repeated log shapes       │
│                                                            │
│  Example A: 1,000 lines like "user X logged in"                │
│             → collapsed into 1 pattern with count=1000           │
│  Example B: Feature disabled (default) → no pattern data         │
│             collected at all                                      │
└───────────────────────────────────────────────────────┘
```

### 🌸 Bloom Planner / Builder / Gateway (Experimental)

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Three-part experimental system to speed up    │
│              filtering via bloom filters                     │
│  CONTAINS:                                                    │
│    Planner → task queue for what needs building                │
│    Builder → stateless workers that build bloom blocks           │
│    Gateway → serves filter-match requests to Index Gateway       │
│  WHY IT MATTERS: Lets Loki skip chunks that definitely don't     │
│    match a filter, before even fetching them                      │
│                                                            │
│  Example A: New series added today                              │
│             → Planner schedules a "build" task                    │
│  Example B: Existing series, no changes                          │
│             → Planner skips it (already built)                     │
└───────────────────────────────────────────────────────┘
```

## Full Lifecycle Diagram

```
1️⃣  Client sends log stream {foo="bar", bazz="buzz"}
        ▼
2️⃣  🧑‍💼 Distributor validates + sorts labels → {bazz="buzz", foo="bar"}
        ▼
3️⃣  Rate limit checked per tenant (global limit ÷ #distributors)
        ▼
4️⃣  Consistent hash ring picks 3 Ingesters (Replication Factor=3)
        ▼
5️⃣  🗄️ Ingesters write to WAL + build in-memory chunk
       (quorum of 2/3 required to ACK the write)
        ▼
6️⃣  Chunk flushed (capacity/time/manual) → hashed by
       tenant+labels+contents → sent to 🏛️ Object Storage
        ▼
7️⃣  🗜️ Compactor later merges per-tenant/day index files,
       applies retention & deletion
       (in parallel: ⏰ Ruler evaluates alerts,
        🐝 Pattern Ingester detects patterns,
        🌸 Bloom Planner/Builder/Gateway build & serve blooms)

  ── READ PATH (any time after write) ──
  Client Query
        ▼
  📞 Query Frontend splits/caches query
        ▼
  🎟️ Query Scheduler queues fairly per tenant (optional)
        ▼
  🕵️ Querier pulls job → checks 🗄️ Ingesters (recent) +
       📇 Index Gateway (chunk refs) → 🏛️ Object Storage
        ▼
  Querier deduplicates results (timestamp+labels+message)
        ▼
  Result returned to client
```

## Key Takeaways

**Write path:**
- ✅ **Distributor** validates, normalizes, and rate-limits — it's stateless and disposable.
- ✅ **Replication Factor** (usually 3) + **quorum** (2 of 3) protect against Ingester loss during rollout.
- ✅ **Write-Ahead Log** + replication together prevent true data loss.

**Read path:**
- ✅ **Query Frontend** splits and caches; **Query Scheduler** adds fair per-tenant queuing.
- ✅ **Querier** merges recent in-memory data with archived data and deduplicates.
- ✅ **Index Gateway** tells the Querier exactly which chunks to fetch.

**Background maintenance:**
- ✅ **Compactor** keeps the index lean and enforces retention.
- ✅ **Ruler** turns queries into alerts on a schedule.
- ✅ **Bloom** trio (experimental) speeds up filtering by skipping non-matching chunks.

**One-line flow:**
`Client ➡ Distributor ➡ Ingester (WAL+chunks) ➡ Object Storage ➡ [Compactor cleans index] ➡ Query Frontend ➡ Query Scheduler ➡ Querier ➡ Index Gateway ➡ Client`

## Memory Trick 🧠

> **"D-I go in, Q-Q-Q come out."**
> - **D**istributor and **I**ngester handle logs going **IN** (write path).
> - **Q**uery Frontend, **Q**uery Scheduler, and **Q**uerier bring logs back **OUT** (read path).
> - Everything else (Compactor, Ruler, Index Gateway, Bloom*, Pattern Ingester) is **support crew** working in the background on both sides.

## Plain-Language Summary

The original Grafana Loki documentation describes Loki as a modular logging system built from separate components that each own one job. On the **write path**, the Distributor receives, validates, and load-balances incoming logs across replicated Ingesters, which buffer logs in memory (backed by a write-ahead log for safety) before flushing compressed "chunks" to long-term object storage. On the **read path**, an optional Query Frontend and Query Scheduler organize and speed up queries before handing work to Queriers, which pull data from both the Ingesters (recent, in-memory) and the backend store (via the Index Gateway, which knows exactly which chunks to fetch), then deduplicate results before returning them. Supporting this, the Compactor merges and cleans up index files and enforces retention, the Ruler evaluates alerting/recording rules, the optional Pattern Ingester detects recurring log patterns, and the experimental Bloom Planner/Builder/Gateway trio builds and serves bloom filters to skip irrelevant chunks during queries. All of these components can run together as a single binary, in three logical groups (read/write/backend), or fully independently, depending on how much a deployment needs to scale.
