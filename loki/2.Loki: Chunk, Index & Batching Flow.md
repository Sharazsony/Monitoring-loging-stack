# Grafana Loki: Chunk, Index & Batching Flow — Complete Understanding Guide 📊

## One-Sentence Answer

**Log lines get batched twice — once by the agent before sending, once by Loki before storing — and the index for a chunk is only written the instant that chunk is flushed, so there's always a delay between "log happened" and "index is globally searchable."**

---

## Analogy Section 📮

Think of this like a **post office sorting depot**.

```
┌──────────────────────────────────────────────────────────────────┐
│                     📮 THE POST OFFICE ANALOGY                    │
│                                                                    │
│   ✍️ Letters          📦 Mail Bag         🏢 Sorting Office       │
│   (log lines)      (agent batch)         (Loki ingester)         │
│                                                                    │
│   📇 Card Catalog                        🗄️ Central Archive       │
│   (in-memory index)                     (object store)           │
│                                                                    │
└──────────────────────────────────────────────────────────────────┘
```

1. ✍️ You write letters (log lines) one at a time.
2. 📦 A courier (agent) doesn't run to the post office per letter — they wait until the bag is full or a timer runs out, then drive over.
3. 🏢 The sorting office (ingester) drops incoming letters into a bin per sender-address (stream/label set).
4. 📇 As soon as a *new* sender-address shows up, the front-desk card catalog notes it instantly — so if someone asks "has this sender shown up yet?" the answer is immediate, even before the bin is fully packed.
5. 🗄️ The bin only gets shipped to the central archive once it's full or old enough — and only *then* does the archive's real catalog entry get written.

## Complete Data/Process Flow

### Step 0 — Agent-Side Batching (Promtail / Alloy / etc.)

```
┌─────────────────────────────────────────────┐
│  LOG AGENT (Promtail / Alloy / etc.)         │
│                                               │
│  Log line 1 ─┐                               │
│  Log line 2 ─┤                               │
│  Log line 3 ─┼──► buffered in memory         │
│  Log line 4 ─┤                               │
│  Log line 5 ─┘                               │
│                                               │
│  Flush triggered by whichever hits first:    │
│   • batchwait  (e.g. ~1s)                    │
│   • batchsize  (e.g. ~1 MiB)                 │
│                                               │
│  ──► single HTTP POST to /loki/api/v1/push   │
│      grouped by label set (stream)           │
└─────────────────────────────────────────────┘
```

💡 **Key insight:** This is a *separate, earlier* layer of batching from anything inside Loki. Its only job is to cut down HTTP request overhead — it has nothing to do with chunks or indexing yet.

---

### Step 1 — Stream Registration (In-Memory Index)

```
┌─────────────────────────────────────────────┐
│  INGESTER receives pushed batch              │
│                                               │
│  New label set seen? {job="app", env="prod"} │
│        │                                     │
│        ▼                                     │
│  📇 In-memory index entry created INSTANTLY   │
│     (lets live queries find this stream      │
│      even before anything is flushed)        │
└─────────────────────────────────────────────┘
```

💡 **Key insight:** This happens the *moment a new stream first appears* — not on any timer. It's why very recent, unflushed logs are still queryable.

---

### Step 2 — Chunk Building & Flush

```
┌─────────────────────────────────────────────┐
│  Lines for a stream accumulate into a CHUNK  │
│                                               │
│  Flush triggered by whichever hits first:    │
│   • chunk_target_size                        │
│   • max_chunk_age                            │
│   • chunk_idle_period                        │
│        │                                     │
│        ▼                                     │
│  📦 Chunk flushed → object store (instant)    │
│  📇 Durable index entry written (SAME instant)│
└─────────────────────────────────────────────┘
```

💡 **Key insight:** The chunk (data) and its durable index entry (label set → chunk location) are written **at the exact same moment** — not on separate schedules, and never per individual line.

---

### Step 3 — Index Shipping Delay

```
┌─────────────────────────────────────────────┐
│  Local index file (BoltDB / TSDB)            │
│                                               │
│  New file started every 15-minute window     │
│        │                                     │
│        ▼                                     │
│  Shipper uploads a file ONLY once it's no    │
│  longer the "active" file for that window    │
│        │                                     │
│        ▼                                     │
│  🗄️ Index becomes visible to OTHER components │
│     up to ~15 minutes after the chunk itself  │
│     was already readable in the object store  │
└─────────────────────────────────────────────┘
```

💡 **Key insight:** The **chunk** is readable immediately once flushed. The **index that points to it** can lag up to ~15 minutes behind. This gap is the classic cause of "why can't I query logs I just ingested."

## Deep Dive Sections

### 📦 The Chunk

**What it is:** A compressed block of log lines belonging to one stream (one label set), built up in memory before being written to the object store.

**What it contains:** Raw log lines + timestamps for a single label set, batched together until a size/age/idle threshold is hit.

**Why it matters:** It's the actual data Loki reads at query time — everything else (index) just points to it.

| Scenario A | Scenario B |
|---|---|
| `{job="app", env="prod"}` — high volume, hits `chunk_target_size` quickly → flushes in seconds | `{job="cron", env="prod"}` — low volume, sits idle → flushes only when `chunk_idle_period` expires, maybe minutes later |

---

### 📇 The In-Memory Index (Stream Registration)

**What it is:** A live, instantly-updated map of "which label sets currently exist" inside the ingester.

**What it contains:** Label set → active stream reference (not yet pointing to durable storage).

**Why it matters:** It's what makes very recent, not-yet-flushed logs queryable at all.

| Scenario A | Scenario B |
|---|---|
| First log line ever seen for `{app="checkout"}` → entry created the instant it arrives | 10,000th log line for `{app="checkout"}` → no new entry, just appended to the existing stream |

---

### 📇 The Durable Index (BoltDB-shipper / TSDB)

**What it is:** The persisted record of label set → chunk location, written to local disk then shipped to shared storage.

**What it contains:** For TSDB — index files built alongside chunk flush. For boltdb-shipper — a BoltDB file per 15-minute window.

**Why it matters:** This is what every *other* Loki component (queriers, other ingesters) relies on to find chunks — and it's the piece with the shipping delay.

| Scenario A | Scenario B |
|---|---|
| Chunk flushes at 10:02, inside the active 10:00–10:15 window → index entry sits local-only until ~10:15 | Chunk flushes at 10:14, right before the window rolls → shipped almost immediately after |

---

### 🗄️ The Object Store

**What it is:** Shared durable storage (S3, GCS, etc.) holding both flushed chunks and shipped index files.

**What it contains:** Immutable chunk files + periodically-shipped index files.

**Why it matters:** It's the single source of truth all Loki components eventually converge on, but chunks and their index entries don't always land there at the same time.

## Full Lifecycle Diagram

```
1️⃣ Log line written by app
        ▼
2️⃣ Agent buffers lines (batchwait / batchsize)
        ▼
3️⃣ Agent POSTs batch → Loki ingester
        ▼
4️⃣ New stream? → 📇 in-memory index entry created INSTANTLY
        ▼
5️⃣ Lines accumulate into a chunk until threshold hit
        ▼
6️⃣ Chunk flush → 📦 object store (instant) + 📇 durable index write (SAME instant, local)
        ▼
7️⃣ Index file shipped to shared object store (up to ~15 min later)
```

## Comparison Example

| What changes | What stays the same |
|---|---|
| Agent `batchwait=1s` vs `batchwait=5s` → HTTP POSTs happen more/less often | The chunk-flush thresholds (`chunk_target_size`, `max_chunk_age`, `chunk_idle_period`) are untouched — those live entirely inside Loki, independent of agent settings |
| A busy stream flushes its chunk in seconds | A quiet stream might take until `chunk_idle_period` expires — but in **both** cases, the index write happens at the *same instant* as that stream's own flush |

## Key Takeaways

**✅ Batching happens twice, for different reasons**
- Agent batching (sub-second, ~1 MiB) exists purely to cut HTTP overhead.
- Loki chunk batching (much larger, slower) exists to reduce storage file count and pair data with its index.

**✅ Index timing has two very different speeds**
- In-memory index: instant, on first stream appearance.
- Durable/shipped index: tied to chunk flush, then delayed up to ~15 min to become globally visible.

**✅ Chunk and durable index are never separate events**
- They are written at the exact same moment — never on independent schedules, never per individual line.

**Flow summary:**
`App log line → Agent batch → Loki push → In-memory index (instant) → Chunk buffer → Chunk flush + durable index (same instant) → Index shipped (~15 min lag) → Globally queryable`

---

## Memory Trick 🧠

**"Two catalogs, one clock."**
- The **in-memory catalog** ticks the instant a new stream walks in the door (fast, temporary).
- The **durable catalog** only gets stamped when the chunk itself is boxed up and shipped — same clock, same instant — but that stamped box still has to wait for the delivery truck (~15 min) before the rest of the building can see it.

---

## Plain-Language Summary

The original source explained that Loki doesn't index log lines one at a time — it batches. There are two layers of batching before anything becomes globally searchable: first, the log-shipping agent (like Promtail) buffers lines in memory and sends them in a single HTTP push once a time or size limit is hit. Second, inside Loki itself, those pushed lines accumulate into a per-stream chunk, and only when that chunk hits its own size/age/idle threshold does it get flushed to the object store — at which point the durable index entry pointing to it is written at that exact same instant. There's also a separate, instant in-memory index that registers a stream the moment it's first seen, which is why very recent logs can still be queried even before their chunk has flushed. The final piece is a shipping delay: the local index file isn't pushed to shared storage until it's no longer the "active" file for its 15-minute window, so the durable index can lag up to ~15 minutes behind the chunk data it describes — even though the chunk itself is already readable.
