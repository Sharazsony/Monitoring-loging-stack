# Loki Cluster Sizing : Complete Understanding Guide 📊

---

## 🎯 One-Sentence Answer

**Grafana Loki sizes its cluster by splitting log-processing work across seven specialized components (Ingester, Distributor, Index Gateway, Querier, Query-Frontend, Query-Scheduler, Compactor), each given its own CPU/Memory budget and replica count based on how much log data (TB/day) the system ingests.**

---

## 🏭 Analogy Section — The Loki Cluster as a Busy Post-Sorting Warehouse

Think of Loki as a **giant mail-sorting warehouse** that receives, stores, and retrieves millions of letters (log lines) every day.

```
┌──────────────────────────────────────────────────────────────────────┐
│                  🏭 THE LOKI MAIL-SORTING WAREHOUSE                   │
│                                                                        │
│   📬 Trucks arrive with mail          ─────►  📮 Distributor          │
│   (raw log lines pouring in)                  (sorts by route/label)  │
│                                                                        │
│   📦 Sorted mail gets boxed           ─────►  📥 Ingester             │
│   (batched into chunks)                       (packs & stores boxes)  │
│                                                                        │
│   🗂️ A card catalog is kept           ─────►  🗃️ Index Gateway        │
│   (so any box can be found fast)              (label lookup desk)     │
│                                                                        │
│   🧹 Old boxes get merged/cleaned     ─────►  🧹 Compactor            │
│   (housekeeping, one janitor total)           (singleton cleanup)     │
│                                                                        │
│   🙋 Customer asks "find my letter"   ─────►  🎫 Query-Scheduler      │
│   (request enters a queue)                    (hands out queue tickets)│
│                                                                        │
│   🧑‍💼 Front desk splits big requests  ─────►  🖥️ Query-Frontend       │
│   into smaller jobs                           (task splitter)         │
│                                                                        │
│   🔍 Workers fetch the actual boxes   ─────►  🔎 Querier              │
│   (do the real searching)                     (the search workforce)  │
└──────────────────────────────────────────────────────────────────────┘
```

**Process in plain steps:**
1. Mail (logs) arrives at the loading dock.
2. It's sorted and routed (**Distributor**).
3. It's packed into boxes and shelved (**Ingester**).
4. A catalog entry is made so it can be found later (**Index Gateway**).
5. Old boxes are periodically cleaned/merged by one janitor (**Compactor**).
6. When a customer wants a letter, the request is queued (**Query-Scheduler**), split into smaller jobs (**Query-Frontend**), and workers go fetch it (**Querier**).

## 🔬 Deep Dive Sections

### 📥 Ingester

```
┌──────────────────────────────────────────────────────────┐
│  📥 INGESTER                                               │
│  WHAT: Receives and temporarily holds incoming log data     │
│        before flushing it to long-term storage.             │
│  CONTAINS: In-memory chunks of recent logs, ready to be      │
│            flushed to object storage.                        │
│  WHY IT MATTERS: It's the FIRST place data lands and         │
│            has the HIGHEST base replica count (6) and        │
│            heaviest total CPU (12) in the smallest tier —     │
│            because every single log line must pass through   │
│            it.                                                │
│                                                                │
│  Example A (Tier: <100TB/mo)     Example B (same table)       │
│  CPU: 2 | Mem: 4Gi | Reps: 6     Total CPU: 2×6 = 12          │
│  ─────────────────────────       Total Mem: 4×6 = 24Gi        │
└──────────────────────────────────────────────────────────┘
```

### 📮 Distributor

```
┌──────────────────────────────────────────────────────────┐
│  📮 DISTRIBUTOR                                             │
│  WHAT: The entry-point component that receives log pushes    │
│        and routes/hashes them to the correct ingesters.      │
│  CONTAINS: Routing logic based on label hashing (no log       │
│            storage itself).                                   │
│  WHY IT MATTERS: Needs decent CPU (2) but very LITTLE          │
│            memory (0.5Gi) — it's a traffic cop, not a          │
│            warehouse.                                          │
│                                                                  │
│  Compare to Ingester:            Compare to Compactor:          │
│  Distributor Mem = 0.5Gi         Compactor Mem = 10Gi           │
│  (light — just routes)           (heavy — merges big files)     │
└──────────────────────────────────────────────────────────┘
```

### 🗃️ Index Gateway

```
┌──────────────────────────────────────────────────────────┐
│  🗃️ INDEX GATEWAY                                           │
│  WHAT: Serves index lookups so queries know WHICH chunks      │
│        of data to fetch, without loading full indexes         │
│        into every querier.                                     │
│  CONTAINS: Label/series index shards.                          │
│  WHY IT MATTERS: Low CPU (0.5) but meaningful memory (2Gi)      │
│            per replica — index data is memory-hungry but        │
│            not compute-hungry.                                   │
│                                                                    │
│  Example A: 4 replicas → Total CPU = 2, Total Mem = 8Gi           │
│  Example B: If replicas doubled to 8 → Total CPU = 4, Mem = 16Gi  │
│  (scales linearly with replica count)                             │
└──────────────────────────────────────────────────────────┘
```

### 🔎 Querier

```
┌──────────────────────────────────────────────────────────┐
│  🔎 QUERIER                                                 │
│  WHAT: Executes the actual LogQL queries against stored       │
│        chunks and the index.                                   │
│  CONTAINS: Query execution engine (fetches & filters logs).    │
│  WHY IT MATTERS: Has the HIGHEST replica count (10) in the      │
│            base table, but the guidance warns this can            │
│            balloon 10x with unoptimised queries.                  │
│                                                                     │
│  Example A (Baseline):            Example B (Unoptimised query):   │
│  1 CPU × 10 reps = 10 CPU total   Could require up to 100 CPU      │
│  1Gi × 10 reps = 10Gi total       total if queries are inefficient │
└──────────────────────────────────────────────────────────┘
```

### 🖥️ Query-Frontend

```
┌──────────────────────────────────────────────────────────┐
│  🖥️ QUERY-FRONTEND                                          │
│  WHAT: Splits and schedules large queries into smaller         │
│        sub-queries before handing them to queriers.             │
│  CONTAINS: Query splitting/sharding logic, results cache        │
│            coordination.                                          │
│  WHY IT MATTERS: Only needs 2 base replicas — it's a              │
│            coordination layer, not a heavy compute layer.          │
│                                                                      │
│  Compare Query-Frontend (2 CPU total, 4Gi total) to                 │
│  Query-Scheduler (2 CPU total, 1Gi total) — Frontend needs           │
│  MORE memory because it holds query-splitting state.                 │
└──────────────────────────────────────────────────────────┘
```

### 🎫 Query-Scheduler

```
┌──────────────────────────────────────────────────────────┐
│  🎫 QUERY-SCHEDULER                                          │
│  WHAT: Queues and dispatches query jobs to available            │
│        queriers, decoupling frontend from querier scaling.       │
│  CONTAINS: A job queue for pending sub-queries.                   │
│  WHY IT MATTERS: Lightest memory footprint of all query-           │
│            path components (0.5Gi per replica) — it just            │
│            holds queue metadata, not query data.                     │
│                                                                        │
│  Note: The doc says parallel-querier & related components can         │
│  be sized "the same" as queriers depending on how much Loki            │
│  rules (recording/alerting rules) are used.                             │
└──────────────────────────────────────────────────────────┘
```

### 🧹 Compactor

```
┌──────────────────────────────────────────────────────────┐
│  🧹 COMPACTOR                                                │
│  WHAT: Merges and compacts index/chunk files for storage        │
│        efficiency and retention enforcement.                     │
│  CONTAINS: Background compaction jobs.                            │
│  WHY IT MATTERS: The ONLY component that is a forced               │
│            SINGLETON (1 replica always) — running more than         │
│            one would corrupt compaction state. Also has the          │
│            HIGHEST memory-per-replica (10Gi) of any component.        │
│                                                                          │
│  Example A: 1 replica, 2 CPU, 10Gi → Totals = 2 CPU / 10Gi              │
│  Example B: Even at massive scale (~1PB/month tier), it              │
│  STILL stays "1 (Singleton)" — never horizontally scaled.               │
└──────────────────────────────────────────────────────────┘
```

## 🔗 Full Lifecycle Diagram — End to End

```
1️⃣  📬 Logs pushed into the cluster (raw log lines, any volume)
        ▼
2️⃣  📏 Classify by ingestion tier: <100TB/mo | 100TB–1PB/mo | ~1PB/mo
        ▼
3️⃣  📮 Distributor (2 CPU / 0.5Gi × 4 reps) routes logs by label hash
        ▼
4️⃣  📥 Ingester (2 CPU / 4Gi × 6 reps) buffers & flushes chunks to storage
        ▼
5️⃣  🗃️ Index Gateway (0.5 CPU / 2Gi × 4 reps) records label/series index
        ▼
6️⃣  🧹 Compactor (2 CPU / 10Gi × 1 singleton) periodically merges/cleans
        ▼
7️⃣  🙋 Query arrives → 🎫 Query-Scheduler queues it → 🖥️ Query-Frontend
        splits it → 🔎 Querier (1 CPU / 1Gi × 10 reps) fetches & returns data
        ▼
   ☁️  All of the above run on AWS M6+/T2+ or GCP E2+ nodes;
       if ingestion ≥ 30TB/day, add NVMe memcached-extstore nodes
```

## ✅ Key Takeaways

**On Tiering:**
- ✅ Loki gives **three separate sizing tables** based on daily/monthly ingestion volume: <3TB/day, 3–30TB/day, and ~30TB/day.
- ✅ These numbers are a **starting baseline**, not a guarantee — real workloads vary.

**On Components:**
- ✅ **Ingester** and **Querier** get the most replicas — they're the workhorses.
- ✅ **Compactor** is always a **singleton** — never horizontally scaled.
- ✅ **Distributor** and **Query-Scheduler** are lightweight on memory — they coordinate, not store.

**On Query Performance:**
- ✅ Poorly written queries can require **up to 10x** the suggested querier resources.
- ✅ **Horizontal autoscaling** is the recommended cost-effective fix, not permanently over-provisioning.

**On Caching:**
- ✅ **memcached-extstore** (disk-based cache) is only worth the added complexity at **≥30TB/day (~1PB/month)** ingestion.

**On Infrastructure:**
- ✅ General-purpose cloud instances (AWS M6+/T2+, GCP E2+) cover most components.
- ✅ NVMe storage-optimised nodes are reserved specifically for the caching layer.

**One-line flow:**
📬 Logs In → 📮 Distributor → 📥 Ingester → 🗃️ Index Gateway → 🧹 Compactor (cleanup) → 🎫 Scheduler → 🖥️ Frontend → 🔎 Querier → 🙋 Results Out

## 🧠 Memory Trick

**"IDIQ-FSC"** — remember the seven components in pipeline order:

> **I**ngester eats the logs, **D**istributor directs them,
> **I**ndex gateway catalogs them, **Q**uerier finds them,
> **F**rontend splits the ask, **S**cheduler queues the ask,
> **C**ompactor cleans up after everyone else.

Or simpler: **"The Compactor is the lonely janitor"** — it's the ONE component that NEVER gets more replicas, no matter how big your cluster grows. Every other component scales out; the Compactor scales *up* (bigger box) but never *out* (more boxes).

## 📄 Plain-Language Restatement of the Source

The original Grafana Loki documentation page explains how to size a Loki logging cluster in **microservices/distributed mode**. It provides a resource-sizing table (CPU request, memory request, and base replica count) for seven core components — Ingester, Distributor, Index Gateway, Querier, Query-Frontend, Query-Scheduler, and Compactor — broken into three ingestion-volume tiers: under 100TB/month, 100TB to 1PB/month, and around 1PB/month. It also gives general query-performance advice (run small, numerous queriers; watch for unoptimised queries needing up to 10x resources; use horizontal autoscaling), a rule for when disk-based caching (memcached-extstore) becomes worthwhile (only above ~30TB/day ingestion), and recommended cloud instance families for AWS (M6+/T2+) and GCP (E2+), plus NVMe storage-optimised nodes for the caching layer specifically.
