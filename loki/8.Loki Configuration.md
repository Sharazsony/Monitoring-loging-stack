# 1. How to Use This Guide

This guide turns the full Grafana Loki configuration reference into a structured
learning path. It is organized so you can go **top to bottom** as a course, or
jump straight to a chapter as a **reference** while writing a real `loki.yaml`.

Each configuration block below follows the same pattern:

1. **What it is** — plain-English purpose.
2. **When you touch it** — the real-world situation that makes you edit it.
3. **Key fields** — the parameters that matter 95% of the time (with defaults).
4. **Example YAML** — copy-paste starting point.
5. **Gotchas / best practice** — what breaks in production if you get it wrong.

By the end you will understand every major block of Loki's configuration file,
how the pieces fit together, how Loki is deployed, and how to tune it safely.

---

# 2. The Big Picture: What Loki's Config Actually Controls

Loki is a **log aggregation system** built like a distributed database that is
optimized to be cheap and simple: instead of indexing full log text (like
Elasticsearch), Loki indexes only a small set of **labels** per stream and
stores the raw log content compressed in **chunks** in object storage.

Because Loki can run as a single process or as dozens of specialized
microservices, its configuration file (commonly `loki.yaml` or `config.yaml`)
is really a **union of every component's settings**. You only need to touch
the parts relevant to the component(s) you're running.

```
                         ┌─────────────┐
   clients (Alloy,       │ Distributor │  <- receives writes, validates,
   Promtail, Fluent) ───▶│             │     hashes streams, forwards
                         └──────┬──────┘
                                │
                         ┌──────▼──────┐
                         │  Ingester   │  <- buffers, builds chunks, WAL
                         └──────┬──────┘
                                │  (flush)
                         ┌──────▼──────┐
                         │Object Store │  <- S3 / GCS / Azure / Filesystem
                         │ (chunks +   │
                         │  index)     │
                         └──────┬──────┘
                                │
     ┌─────────────┐    ┌──────▼──────┐    ┌──────────────┐
     │Query Frontend│◀──▶│   Querier   │◀──▶│Index Gateway │
     └──────┬───────┘    └─────────────┘    └──────────────┘
            │
     ┌──────▼──────┐
     │   Grafana    │  <- LogQL queries
     └─────────────┘
```

Supporting components you configure alongside this pipeline:

| Component | Purpose |
|---|---|
| **Compactor** | Merges/compacts index files, applies retention & deletion |
| **Ruler** | Evaluates recording/alerting rules against log data |
| **Query Scheduler** | Decouples query queueing from the frontend for large clusters |
| **Bloom Planner/Builder/Gateway** | Experimental bloom filters to skip chunks that can't match a query |
| **Pattern Ingester** | Detects and clusters recurring log patterns ("log patterns" feature) |

# 3. Anatomy of the Config File

## 3.1 How Loki loads config

```bash
loki -config.file=/etc/loki/loki.yaml
```

- `-config.file` accepts a **comma-separated list of paths** — the first
  existing file wins.
- If you don't pass it, Loki looks for `config.yaml` in the current directory
  and in `./config/`.
- Every setting can *also* be set as a CLI flag (shown as `# CLI flag:` in the
  reference). **YAML always wins if both are set for the same field** unless
  documented otherwise for that field.

## 3.2 Printing the effective config (debugging superpower)

```bash
loki -config.file=loki.yaml -print-config-stderr
# or, ordered so it reads top-to-bottom in Grafana Explore logs:
loki -config.file=loki.yaml -log-config-reverse-order
```

This dumps **every** field Loki will actually run with — defaults, file
overrides, and flag overrides combined. This is the #1 tool for diagnosing
"why is Loki not doing what I configured" issues, because it shows you the
merged truth, not just what you typed.

## 3.3 Environment variable substitution

Available from Loki 2.1+. Enable with the CLI flag:

```bash
loki -config.file=loki.yaml -config.expand-env=true
```

Then in YAML:

```yaml
storage_config:
  aws:
    s3: s3://${AWS_ACCESS_KEY_ID}:${AWS_SECRET_ACCESS_KEY}@${AWS_REGION}
```

- `${VAR}` → replaced by the env var's value.
- `${VAR:-default}` → replaced by `default` if `VAR` is unset.
- Substitution happens **before** YAML parsing, and is **case-sensitive**.
- Undefined variables with no default become an **empty string** — a common
  silent-bug source, so always use `:-default` for anything optional.

## 3.4 Generic placeholder types used throughout the reference

| Placeholder | Meaning | Example |
|---|---|---|
| `<boolean>` | `true` / `false` | `true` |
| `<int>` | plain integer, or size with unit suffix (`B,KB,MB,GB,TB,PB,EB`) | `256KB` |
| `<duration>` | number + unit. Prometheus-style fields: `ms,s,m,h,d,w,y`. Go-native fields: `ns,us,µs,ms,s,m,h` only (no `d`/`w`/`y`) | `30s`, `1h`, `1d` |
| `<labelname>` | regex `[a-zA-Z_][a-zA-Z0-9_]*` | `job` |
| `<labelvalue>` | any unicode string | `"nginx"` |
| `<filename>` | relative or absolute path | `/etc/loki/rules` |
| `<host>` | hostname/IP + optional port | `localhost:9095` |
| `<string>` | plain string | `"hello"` |
| `<secret>` | a string treated as a secret (password/token) | `"s3cr3t"` |

**Rule of thumb:** brackets `[ ]` around a key in the reference mean the field
is *optional* and shows its default; no brackets means it's effectively
structural (a nested block).

# 4. Deployment Modes (`target`)

The single most important top-level field is `target`. It decides **which
components actually start** inside this process.

```yaml
target: all   # default — monolithic / single-binary mode
```

| Value | What starts | Use case |
|---|---|---|
| `all` | Every component in one process | Local dev, small/simple production |
| `read` | Querier + query-frontend (read path) | "Simple scalable" deployment, read replica |
| `write` | Distributor + ingester + compactor (write path) | "Simple scalable" deployment, write replica |
| `distributor`, `ingester`, `querier`, `query-scheduler`, `query-frontend`, `index-gateway`, `ruler`, `compactor`, `table-manager`, `ingester-querier`, ... | One specific microservice | Full microservices deployment (large scale) |

Run `loki -list-targets` to print the full, version-accurate list.

**Three canonical deployment patterns:**

1. **Monolithic (`all`)** — one binary, one process. Easiest to operate,
   scales vertically. Good up to a few hundred GB/day.
2. **Simple Scalable Deployment (SSD)** — `read` and `write` targets (plus a
   `backend` target in newer versions) as separate deployments, so you can
   scale reads and writes independently without full microservices
   complexity. Grafana's own recommended default for most production users.
3. **Microservices** — every component (`distributor`, `ingester`, `querier`,
   `compactor`, `query-frontend`, `query-scheduler`, `index-gateway`,
   `ruler`, ...) runs as its own deployment. Maximum control and
   independent scaling, maximum operational complexity. Used at very large
   scale (hundreds of TB/day).

# 5. Authentication & Multi-Tenancy

```yaml
auth_enabled: true
```

- `true` (default): every request **must** include an `X-Scope-OrgID` header.
  This is Loki's **tenant ID** — Loki is multi-tenant by design, and this
  header is how it separates data between tenants.
- `false`: all requests are treated as a single fake tenant called `fake`.
  Fine for local testing; **never** do this in a shared production system.

> Loki ships with **no built-in authentication layer**. `X-Scope-OrgID` is
> only a tenant *identifier*, not a credential. You must put an
> authenticating reverse proxy (nginx, an API gateway, Grafana's built-in
> proxy, etc.) in front of Loki to actually verify who is allowed to send
> that header.

# 6. The `server` Block — Network & HTTP/gRPC Tuning

Every Loki process runs an HTTP server (default port **3100**) and a gRPC
server (default port **9095**) for internal component-to-component traffic.

```yaml
server:
  http_listen_port: 3100
  grpc_listen_port: 9095
  http_listen_address: ""      # "" = all interfaces
  grpc_server_max_recv_msg_size: 4194304   # 4 MB
  grpc_server_max_send_msg_size: 4194304   # 4 MB
  grpc_server_max_concurrent_streams: 100
  log_level: info
  log_format: logfmt           # or "json"
  http_server_read_timeout: 30s
  http_server_write_timeout: 30s
  graceful_shutdown_timeout: 30s
```

**Key fields to know:**

| Field | Default | Why it matters |
|---|---|---|
| `http_listen_port` / `grpc_listen_port` | `3100` / `9095` | Change when co-locating multiple Loki processes on one host |
| `grpc_server_max_recv_msg_size` | 4 MB | **Very commonly increased** — large batch pushes or big query responses hit this ceiling first, showing as gRPC "received message larger than max" errors |
| `log_level` | `info` | Set to `debug` temporarily when troubleshooting, never leave on long-term (huge log volume) |
| `http_tls_config` / `grpc_tls_config` | disabled | Configure `cert_file`/`key_file`/`client_ca_file` to run Loki with TLS between components |
| `cluster_validation` | disabled | Optional safety net so a component only accepts requests carrying a matching cluster label |

**Gotcha:** the *server's* `grpc_server_max_recv_msg_size` is separate from
the **client-side** `grpc_client.max_recv_msg_size` used throughout the rest
of the config (ingester client, querier↔frontend client, etc.). If you raise
one without the other, you just move the bottleneck.

# 7. `common` — Share Configuration Instead of Repeating It

The `common` block lets you define storage, replication factor, and ring
settings **once**, and Loki will use those values for every component unless
that component overrides them explicitly. This is the difference between a
20-line config and a 400-line config for the same deployment.

```yaml
common:
  path_prefix: /loki
  replication_factor: 3
  storage:
    s3:
      bucketnames: my-loki-bucket
      region: us-east-1
  ring:
    kvstore:
      store: memberlist
```

**Mental model:** `common.storage` feeds `storage_config`, `ruler.storage`,
etc. `common.ring` feeds every ring-based component (ingester, distributor,
compactor, ruler, index-gateway...) unless that component has its own
explicit `ring:` block. `common.replication_factor` and `common.persist_tokens`
similarly cascade down. **Set it in `common` first; only override per
component when you have a real reason to.**

# 8. Ingestion Path

## 8.1 `distributor` — the front door

The distributor is stateless. It validates incoming pushes, applies
per-tenant limits, computes a hash for each stream, and forwards entries to
the correct ingesters (or Kafka, in newer ingest-limits architectures).

```yaml
distributor:
  ring:
    kvstore:
      store: memberlist
  max_recv_msg_size: 104857600      # 100 MB
  ingester_writes_enabled: true      # classic push path
  kafka_writes_enabled: false        # Kafka-based ingestion path (newer arch)
```

Key concepts:

- **Ring-based routing**: the distributor uses a consistent-hash ring to know
  which ingesters own a given stream, based on `replication_factor`.
- **OTLP ingestion** (`otlp_config`): controls which OpenTelemetry resource
  attributes become **index labels** vs. **structured metadata** — this
  directly affects your cardinality and your storage cost, so treat it
  carefully. Only labels you'll actually filter/group by in LogQL should
  become index labels.
- **Rate limiting**: `distributor` also computes stream *rates* to feed
  `per_stream_rate_limit` enforcement (see `limits_config`).
- **Kafka ingestion** (`kafka_writes_enabled`, `kafka_config` top-level
  block) is Loki's newer decoupled-ingestion architecture — instead of the
  distributor talking to ingesters directly (synchronous, tightly coupled),
  it can write to a Kafka topic that ingesters (or "partition ingesters")
  consume from. This improves durability and scaling but adds an
  operational dependency on Kafka.

## 8.2 `ingester` — where chunks are actually built

The ingester keeps recent log data **in memory**, groups it into per-stream
**chunks**, writes a **Write-Ahead-Log (WAL)** for crash safety, and
periodically **flushes** completed chunks to object storage.

```yaml
ingester:
  chunk_idle_period: 30m
  chunk_target_size: 1572864     # ~1.5 MB compressed — the sweet spot
  chunk_encoding: snappy         # gzip (default) | snappy | lz4 | zstd | flate | none
  max_chunk_age: 2h
  concurrent_flushes: 32
  wal:
    enabled: true
    dir: /loki/wal
    checkpoint_duration: 5m
    flush_on_shutdown: false
    replay_memory_ceiling: 4GB
  lifecycler:
    ring:
      kvstore:
        store: memberlist
      replication_factor: 3
```

### 8.2.1 Chunk lifecycle — the concept you must internalize

A **chunk** is a compressed blob of log lines for **one stream** (one unique
label set). A chunk stops accepting new data and gets flushed when **any** of
these fires first:

1. `chunk_target_size` is reached (best case — a "full" chunk).
2. `chunk_idle_period` passes with no new writes to that stream.
3. `max_chunk_age` is reached (chunk has been open too long, even if it
   never filled).
4. Ingester shuts down (if `flush_on_shutdown: true`, or WAL replay will
   recover it anyway).

**Why this matters for cost & performance:** small, half-empty chunks are
Loki's #1 real-world performance and cost problem. Every chunk carries fixed
overhead (index entries, network calls, S3 object overhead). Thousands of
tiny chunks = thousands of tiny S3 GETs at query time = slow queries + high
storage-API cost. See Chapter 15 (Best Practices) for the concrete fix.

### 8.2.2 Compression algorithm trade-off (`chunk_encoding`)

| Algorithm | Compression ratio | Speed | When to use |
|---|---|---|---|
| `gzip` (default) | Best | Slowest | Low/medium throughput, storage cost sensitive |
| `snappy` | Worst | Fastest | High-throughput environments where CPU/latency matters more than a few % of storage |
| `lz4` | Good (better than snappy) | Slightly slower than snappy | Best all-around compromise for most production clusters |
| `zstd` / `flate` | Tunable | Varies | Specialized tuning scenarios |

### 8.2.3 The Write-Ahead Log (WAL)

The WAL protects **acknowledged but not-yet-flushed** data from being lost if
the ingester process crashes. On restart, Loki replays the WAL to rebuild
in-memory chunks before serving traffic again.

- `wal.replay_memory_ceiling` — caps memory used during replay; if exceeded,
  Loki flushes partial data to storage mid-replay rather than OOMing.
- `wal.disk_full_threshold` — throttles incoming writes once local disk
  usage crosses this ratio, to avoid crashing the ingester with a full disk.
- WAL requires **persistent local disk** — this is why ingesters are
  typically run as a `StatefulSet` in Kubernetes with a PVC, not a stateless
  Deployment.

### 8.2.4 The ring & replication

- `replication_factor` (commonly `3`): every log line is written to N
  ingesters. Loki tolerates `N-1` ingester failures without losing
  unflushed data (assuming quorum-style write behavior upstream).
- `zone_awareness_enabled`: spreads replicas across configured
  `availability_zone` values so a single AZ outage can't take out all
  replicas of a stream.
- `unregister_on_shutdown`: whether an ingester removes itself from the ring
  on clean shutdown (`true` default) vs. staying registered so a restarting
  pod reclaims the same tokens (common trick in Kubernetes rolling
  restarts to avoid unnecessary rebalancing).

### 8.2.5 Kafka-based ingestion (`kafka_ingestion`, `partition_ring`)

Newer Loki versions support ingesting via Kafka partitions instead of (or
alongside) direct ingester writes. This decouples distributor and ingester
lifecycles and is designed for very large, elastic deployments. If you're
not running at that scale, you can safely ignore this and keep
`ingester.kafka_ingestion.enabled: false` (the default).

## 8.3 `pattern_ingester` — automatic log pattern detection

An optional component (disabled by default) that clusters incoming log lines
into detected "patterns" (e.g. recognizing that 10,000 similar lines are
really "the same log template with different IDs"). Useful for the
Explore Logs / pattern-detection UI features in Grafana.

```yaml
pattern_ingester:
  enabled: false
  metric_aggregation:
    loki_address: ""     # where to push aggregated metrics back into Loki
```

## 8.4 `ingester_client` — how the distributor talks to ingesters

```yaml
ingester_client:
  remote_timeout: 5s
  grpc_client_config:
    max_recv_msg_size: 104857600
```

Just a gRPC client configuration wrapper (see §14.5) scoped to
distributor→ingester traffic.

# 9. Query Path

## 9.1 `querier`

```yaml
querier:
  max_concurrent: 4
  query_ingesters_within: 3h
  query_store_only: false
  query_ingester_only: false
```

- `query_ingesters_within`: queries whose time range is entirely older than
  this are sent **only** to the store (object storage), skipping ingesters —
  a useful optimization since ingesters only hold recent data anyway.
- `query_store_only`: forces the querier to *never* ask ingesters — useful
  for a dedicated "historical query" querier pool.
- `query_ingester_only`: the opposite — useful as a fallback mode if object
  storage is temporarily unavailable.
- `max_concurrent`: caps how many queries **this querier process** executes
  simultaneously — your main lever for protecting a querier from being
  overwhelmed by expensive queries.

## 9.2 `query_range` — splitting & caching (query-frontend)

This is where most of Loki's **query performance tuning** lives.

```yaml
query_range:
  align_queries_with_step: false
  cache_results: true
  max_retries: 5
  parallelise_shardable_queries: true
  cache_index_stats_results: true
  cache_volume_results: true
  cache_series_results: true
  cache_label_results: true
```

**Core concept — query splitting:** the frontend breaks a long query into
smaller time-bounded sub-queries (see `split_queries_by_interval` in
`limits_config`, default `1h`) and runs them **in parallel** across queriers,
then merges results. This is *the* reason Loki queries over huge time
ranges don't just time out.

**Core concept — result caching:** once a sub-query's results are computed
they can be cached, so re-running (or extending) a similar query later is
nearly free. Each result type (range query, index stats, volume, series,
label, instant-metric) has its **own** `cache_results`-style toggle and its
own `<x>_results_cache` block so you can size/tune caches independently.

## 9.3 `frontend` — the query-frontend process

```yaml
frontend:
  log_queries_longer_than: 10s
  max_outstanding_per_tenant: 2048
  compress_responses: true
  scheduler_address: ""     # set this OR run without a scheduler
```

- `log_queries_longer_than`: your built-in **slow query log** — set this in
  every production cluster; it's often the fastest way to find the
  LogQL query that's melting your queriers.
- If `scheduler_address` (or the scheduler ring) isn't configured, the
  frontend queues queries itself; if it is, it hands queueing off to a
  dedicated `query_scheduler` component (recommended at scale — decouples
  queueing so a frontend restart doesn't drop the queue).

## 9.4 `query_scheduler`

```yaml
query_scheduler:
  max_outstanding_requests_per_tenant: 32000
  use_scheduler_ring: false
```

Exists purely to **decouple** the query queue from the frontend process
lifecycle in large/microservices deployments. Below a certain scale you
often don't need this component at all.

## 9.5 `frontend_worker` — runs inside the querier

```yaml
frontend_worker:
  frontend_address: ""     # OR
  scheduler_address: ""    # only one of these — never both
```

This is configured **on the querier**, telling it where to pull work from
(either directly from a frontend, or from a scheduler). Exactly one of
`frontend_address` / `scheduler_address` should be set.

## 9.6 `query_engine` — the newer (V2/"Thor") execution engine

```yaml
query_engine:
  enable: false          # experimental next-gen engine
  distributed: false     # experimental distributed execution
  worker_threads: 0      # 0 = GOMAXPROCS
```

An in-progress rewrite of Loki's query execution engine aimed at better
performance on large data-object-based storage. Leave disabled unless you
are deliberately testing it — most fields here are marked **Experimental**.

# 10. Storage: Index + Chunks

This is the part of Loki configuration people find most confusing, because
**three different blocks** interact: `schema_config`, `storage_config`, and
(sometimes) `common.storage`. Here's how they relate:

```
schema_config  → decides WHICH schema/index-type/object-store applies
                 for logs from a given date onward (period_config entries)

storage_config → the actual CONNECTION DETAILS for each object store /
                 index type referenced by schema_config

common.storage → a shortcut to set storage_config (and ruler storage)
                 once instead of repeating it
```

## 10.1 `schema_config` / `period_config`

```yaml
schema_config:
  configs:
    - from: 2024-01-01
      store: tsdb
      object_store: s3
      schema: v13
      index:
        prefix: index_
        period: 24h
```

- `from`: the date this schema config becomes active. **You never edit or
  delete an old period_config entry that has real data behind it** — you
  *add a new one* with a future `from` date when you want to change schema,
  store, or index type. Loki keeps historical entries so it still knows
  how to read old data.
- `store`: `tsdb` (current recommended index type) or the deprecated
  `boltdb-shipper`. Legacy stores (`aws`, `bigtable`, `cassandra`, `gcp`,
  `grpc`) are deprecated — don't use them for new setups.
- `object_store`: which chunk backend to use — `s3` (alias for `aws`),
  `gcs`, `azure`, `alibabacloud`, `bos`, `cos`, `swift`, `filesystem`, or a
  name from `storage_config.named_stores`.
- `schema`: the **index schema version**. `v13` is the current recommended
  version as of this documentation; higher generally means better
  performance/label-storage efficiency.
- `row_shards`: only relevant for schema v10+, controls index sharding.

**Mental model:** think of `schema_config.configs` as a **timeline** of
"rules for how to store data," not a single static setting.

## 10.2 `storage_config`

Holds the literal connection settings keyed by backend name (`aws`, `gcs`,
`azure`, `filesystem`, etc.), plus shipper settings for TSDB/BoltDB index
sync, plus cache settings.

```yaml
storage_config:
  tsdb_shipper:
    active_index_directory: /loki/tsdb-index
    cache_location: /loki/tsdb-cache
    cache_ttl: 24h
  aws:
    s3: s3://us-east-1
    bucketnames: my-loki-bucket
  index_queries_cache_config:
    embedded_cache:
      enabled: true
      max_size_mb: 100
```

### 10.2.1 Object store backends at a glance

| Backend block | Cloud | Notes |
|---|---|---|
| `s3` (`aws_storage_config`) | AWS S3 / S3-compatible (MinIO) | Also has legacy `dynamodb` sub-block (deprecated, index-only) |
| `gcs` (`gcs_storage_config`) | Google Cloud Storage | Auth via service account JSON or ADC |
| `azure` (`azure_storage_config`) | Azure Blob Storage | Supports managed identity, federated token, service principal |
| `alibabacloud` | Alibaba Cloud OSS | |
| `bos` | Baidu Object Storage | |
| `cos` | IBM Cloud Object Storage | |
| `swift` | OpenStack Swift | |
| `filesystem` (`local_storage_config`) | Local disk | Dev/test only — not for real HA production |
| `thanos_object_store_config` | Any of the above via the newer `thanos-io/objstore` client | Opt-in via `-use-thanos-objstore=true`; becoming the future default client library |

### 10.2.2 `named_stores_config` — multiple buckets of the same type

```yaml
storage_config:
  named_stores:
    aws:
      store-1:
        endpoint: s3://foo-bucket
        region: us-west1
```

Then reference `object_store: store-1` in a `period_config` entry. Useful for
migrating buckets, splitting cold/hot storage, or multi-region setups
without duplicating full storage blocks.

## 10.3 `chunk_store_config`

```yaml
chunk_store_config:
  chunk_cache_config:
    embedded_cache:
      enabled: true
```

Controls **chunk-level caching** (as opposed to index caching) — how long
fetched chunks are cached, and an optional two-tier (`_l2`) cache for
overflow.

# 11. `limits_config` — the Single Most Important Block

`limits_config` is where you protect your cluster from noisy tenants,
runaway queries, and cardinality explosions. Every field here is **also**
overridable **per tenant** via the `runtime_config` overrides file (§13),
without restarting Loki.

## 11.1 Ingestion limits

```yaml
limits_config:
  ingestion_rate_strategy: global      # local | global
  ingestion_rate_mb: 10
  ingestion_burst_size_mb: 20
  per_stream_rate_limit: 3MB
  per_stream_rate_limit_burst: 15MB
  max_global_streams_per_user: 10000
  max_label_names_per_series: 15
  max_line_size: 256KB
  reject_old_samples: true
  reject_old_samples_max_age: 168h    # 7 days
```

| Field | What it stops |
|---|---|
| `ingestion_rate_mb` / `ingestion_burst_size_mb` | Total ingest throughput per tenant |
| `per_stream_rate_limit(_burst)` | One noisy stream from starving all others (the #1 real-world cause of "rate limited" errors when one app suddenly logs a stack-trace storm) |
| `max_global_streams_per_user` | **Cardinality explosion** — too many unique label combinations, the #1 cause of Loki performance collapse |
| `max_label_names_per_series` / length limits | Malformed or exploding label sets from misconfigured clients |
| `reject_old_samples_max_age` | Extremely stale writes (clock skew, replay bugs) from silently backfilling |

**`ingestion_rate_strategy: global` vs `local`:** `local` means each
distributor enforces the limit independently (so real cluster-wide limit =
configured value × number of distributors). `global` means the limit is
enforced cluster-wide by having distributors coordinate via their own ring —
almost always what you want in production.

## 11.2 Query limits

```yaml
limits_config:
  max_query_series: 500
  max_query_length: 720h        # 30 days
  max_query_parallelism: 32
  max_entries_limit_per_query: 5000
  max_streams_matchers_per_query: 1000
  query_timeout: 1m
  split_queries_by_interval: 1h
  max_query_lookback: 0s        # 0 = unlimited
```

These are your knobs against **"one bad query takes down the cluster."**
`max_query_length` in particular stops a mistakenly unbounded query (e.g. a
dashboard variable bug) from scanning years of data.

## 11.3 Retention (per tenant / per stream)

```yaml
limits_config:
  retention_period: 744h     # 31 days, 0 = disabled
  retention_stream:
    - selector: '{namespace="dev"}'
      priority: 1
      period: 24h
    - selector: '{container="nginx"}'
      priority: 1
      period: 744h
```

- Retention is **only enforced if the compactor has `retention_enabled: true`**
  (see §12.1) — setting `retention_period` alone does nothing without that.
- `retention_stream` lets specific streams (matched by a label selector) get
  a **different** retention than the tenant default; highest `priority`
  wins on overlap.

## 11.4 Structured metadata, OTLP, and label-derived fields

```yaml
limits_config:
  allow_structured_metadata: true
  max_structured_metadata_size: 64KB
  discover_log_levels: true
  discover_service_name: [service, app, application, app_name, ...]
```

- **Structured metadata** = per-log-line key/value pairs stored **alongside**
  a chunk without becoming index labels (no cardinality cost). This is the
  modern replacement for stuffing everything into labels — e.g. trace IDs,
  request IDs, HTTP status codes belong here, **not** as labels.
  `otlp_config` at this level controls whether OTLP resource/scope/log
  attributes land as index labels, structured metadata, or get dropped —
  get this wrong and you'll either blow up cardinality (too many as labels)
  or lose query-by ability (too many dropped).
- `discover_log_levels` / `discover_service_name`: Loki's automatic field
  detection so Grafana's Explore Logs UI can filter by level/service even
  when your app didn't explicitly label them.

## 11.5 Shard streams (auto-splitting hot streams)

```yaml
limits_config:
  shard_streams:
    enabled: true
    desired_rate: 1536KB    # ~1.5 MB/s triggers a shard split
```

If a single stream is producing more than `desired_rate`, Loki automatically
adds a `__stream_shard__`-style label to split it into multiple parallel
streams so `per_stream_rate_limit` doesn't throttle a genuinely
high-volume — but otherwise healthy — application.

# 12. Compaction, Retention & Deletion

## 12.1 `compactor`

```yaml
compactor:
  working_directory: /loki/compactor
  compaction_interval: 10m
  retention_enabled: true
  retention_delete_delay: 2h
  retention_delete_worker_count: 150
  delete_request_store: s3
```

- **What compaction does:** merges many small per-ingester index files into
  fewer, larger, more query-efficient index files (for `tsdb`/`boltdb-shipper`
  store types).
- **What retention does:** once `retention_enabled: true`, the compactor
  periodically scans for chunks/index entries older than the effective
  `retention_period` (tenant default or `retention_stream` override) and
  marks/deletes them.
- `retention_delete_delay`: a safety buffer — data is marked for deletion
  but not physically removed until this delay passes, giving you a window
  to cancel a mistaken deletion request.
- Only **one compactor should run retention** in a cluster — if using
  `horizontal_scaling_mode`, retention/deletion coordination is handled by
  the designated "main" compactor.

## 12.2 `deletion_mode` (in `limits_config`)

```yaml
limits_config:
  deletion_mode: filter-and-delete   # disabled | filter-only | filter-and-delete
```

Controls whether the **log-line deletion API** (for GDPR-style "delete these
specific lines matching this filter" requests) is available at all, and
whether it actually deletes or just filters matching lines out of query
results without removing underlying data.

# 13. `runtime_config` — Changing Limits Without Restarting Loki

```yaml
runtime_config:
  file: overrides.yaml
  period: 10s
```

Loki polls this file every `period` and **hot-reloads** it — no restart, no
redeploy. This is how you override `limits_config` **per tenant**:

```yaml
# overrides.yaml
overrides:
  tenant1:
    ingestion_rate_mb: 10
    max_streams_per_user: 100000
    max_chunks_per_query: 100000
  tenant2:
    max_streams_per_user: 1000000

multi_kv_config:
  mirror-enabled: false
  primary: consul
```

**Why this matters:** in a multi-tenant Loki (e.g. one Loki cluster serving
many teams/customers), you almost never want to restart the whole cluster to
raise one tenant's rate limit. `runtime_config` is the mechanism that makes
Loki genuinely multi-tenant in practice, not just in theory.

`tenant_limits_allow_publish` (top-level field) whitelists which of these
overridden fields are safe to expose back to tenants via the limits API
endpoint — useful if you want customers to be able to *see* their own limits
without seeing everyone else's tuning.

# 14. Shared Building-Block Configs (Reused Everywhere)

These blocks aren't top-level features on their own — they're **reusable
sub-configs** referenced by many components. Recognizing them means you
already understand half the entire reference, because the same
`<cache_config>`, `<grpc_client>`, `<tls_config>` blocks repeat dozens of
times under different key prefixes.

## 14.1 `cache_config` — used by ~15 different components

```yaml
# example: results cache for the frontend
frontend:
  # ...
results_cache_prefix_example:
  default_validity: 1h
  embedded_cache:
    enabled: true
    max_size_mb: 100
    ttl: 1h
  memcached_client:
    addresses: "dns+memcached-loki:11211"
    timeout: 100ms
  redis:
    endpoint: "redis:6379"
```

Loki supports **three interchangeable cache backends** for almost every
cache in the system:

| Backend | Best for |
|---|---|
| `embedded_cache` | In-process LRU cache — zero extra infra, per-pod, doesn't survive restarts or scale across pods |
| `memcached_client` | Shared, external, the most common production choice |
| `redis` | Shared, external, supports auth/TLS/sentinel, good alternative to memcached |

The **same `cache_config` shape** is reused (with different CLI-flag
prefixes) for: chunk caches (2-tier `l1`/`l2`), index caches (read & write),
query-results caches (range, series, label, volume, instant-metric,
index-stats), and bloom metas caches. Learn this block once, apply it
everywhere.

## 14.2 `tls_config` — used by ~40 different components

```yaml
tls_cert_path: /etc/loki/certs/client.crt
tls_key_path: /etc/loki/certs/client.key
tls_ca_path: /etc/loki/certs/ca.crt
tls_server_name: loki.internal
tls_insecure_skip_verify: false
```

Any client-to-server connection in Loki (ring stores, gRPC clients, memcached,
S3-compatible endpoints, etcd) can be secured with this identical five-field
shape. `tls_insecure_skip_verify: true` should be a temporary debugging
tool only — never a permanent production setting.

## 14.3 `consul` / `etcd` — key-value store backends for rings

Loki's hash rings (ingester ring, distributor ring, compactor ring, ruler
ring, etc.) need a **key-value store** for coordination. Three real choices:

| `store:` value | Notes |
|---|---|
| `memberlist` | **Recommended default.** Gossip-based, no external dependency — Loki nodes talk directly to each other. |
| `consul` | External Consul cluster required. |
| `etcd` | External etcd cluster required. |
| `inmemory` | Single-process only (testing). |
| `multi` | Mirrors writes to a primary + secondary store, used for **live migration** between KV stores with zero downtime. |

```yaml
memberlist:
  join_members:
    - loki-memberlist.loki.svc.cluster.local:7946
  bind_port: 7946
```

**Practical tip:** if you configure `memberlist.join_members` anywhere in the
file, Loki **automatically defaults every ring's `kvstore.store` to
`memberlist`** unless a component explicitly overrides it — this is why most
real-world configs barely mention `consul`/`etcd` at all today.

## 14.4 `backoff_config` — retry policy, reused everywhere

```yaml
backoff_config:
  min_period: 100ms
  max_period: 10s
  max_retries: 10
```

Appears under dozens of blocks (S3 client, DynamoDB, compactor retention,
bloom builder, gRPC clients...). Same idea every time: exponential backoff
between `min_period` and `max_period`, giving up after `max_retries`
(`0` = retry forever in some contexts — check the specific field).

## 14.5 `grpc_client` — internal RPC tuning, reused everywhere

```yaml
grpc_client_config:
  max_recv_msg_size: 104857600
  max_send_msg_size: 104857600
  grpc_compression: snappy
  tls_enabled: false
  backoff_config:
    min_period: 100ms
    max_period: 10s
    max_retries: 10
```

Used by every internal client: ingester client, ruler client, bloom-gateway
client, index-gateway client, query-scheduler client, frontend↔querier
client, and more. If you see mysterious `ResourceExhausted` or
"received message larger than max" gRPC errors in logs, this is the block
(on **both** the client prefix involved **and** the server's
`server.grpc_server_max_recv_msg_size`) you need to raise.

# 15. Best Practices (Production Checklist)

These come directly from Grafana's own operational guidance — treat this as
a pre-launch checklist.

### ✅ 1. Authentication
Loki ships with **no auth layer**. Put an authenticating reverse proxy (nginx,
API gateway, etc.) in front of every Loki endpoint before it's reachable
outside a trusted network.

### ✅ 2. Respect stream time-ordering (if `unordered_writes: false`)
By default Loki now **accepts out-of-order writes globally**. But if you
disable that (`unordered_writes: false`, globally or per tenant via runtime
overrides), remember the rule:

> For any single stream, logs must arrive in **increasing time order**.
> An entry older than the most-recently-received entry **for that exact
> label set** is dropped.

Fix pattern: if two systems can produce out-of-order lines for what would
otherwise be "the same stream," add a distinguishing label (e.g.
`instance="host1"` vs `instance="host2"`) so they become **separate streams**
instead of one out-of-order stream. Never assign timestamps by parsing the
log line itself if the source can jitter — let the shipping agent stamp
receive-time instead, or fix the out-of-order producer.

Out-of-order tolerance window when *enabled*, governed by `max_chunk_age`:

```
earliest_accepted_time = time_of_most_recent_line_in_stream − (max_chunk_age / 2)
```

Example: `max_chunk_age = 2h`, most recent line at 08:00 → earliest accepted
is 07:00. If a new line lands at 10:00, the window slides to 09:00.

### ✅ 3. Pick the right chunk compression for your traffic

| Priority | Choose |
|---|---|
| Lowest storage cost, can tolerate slower ingest | `gzip` (default) |
| Highest ingest throughput / lowest latency | `snappy` |
| Balanced (recommended for most high-throughput prod) | `lz4` |

### ✅ 4. Tune `chunk_target_size` and actually hit it

```yaml
ingester:
  chunk_target_size: 1572864   # 1.5 MB compressed target
  max_chunk_age: 2h
  chunk_idle_period: 30m
```

Rule of thumb: with `snappy`-class compression you need roughly **5–10×
(7.5–10 MB) of raw log data per stream** to fill a 1.5 MB chunk. If you
split traffic into too many streams (too many unique label combinations),
each stream fills more slowly, so **more chunks get flushed early by hitting
`max_chunk_age`/`chunk_idle_period` instead of by actually filling up** —
which means more small, inefficient chunks in storage. **Fewer, higher-label-
cardinality-conscious streams that log fast enough to fill chunks quickly is
better than many thin streams.** Only reach for dynamic/high-cardinality
labels when a stream's natural volume is already high enough to fill chunks
well within `max_chunk_age`.

### ✅ 5. Use the config-dump flags in every environment

```bash
-print-config-stderr        # ad-hoc / CLI usage
-log-config-reverse-order   # standing services (Grafana's own recommendation) —
                             # reversed order reads correctly top-to-bottom in Explore
```

### ✅ 6. Recommended production `limits_config` starting point

```yaml
limits_config:
  ingestion_rate_strategy: global
  ingestion_rate_mb: 10
  ingestion_burst_size_mb: 20
  per_stream_rate_limit: 3MB
  per_stream_rate_limit_burst: 15MB
  max_global_streams_per_user: 10000
  max_streams_per_user: 0          # 0 = rely on the global limit instead
  max_line_size: 256KB
  max_line_size_truncate: false
  max_label_name_length: 1024
  max_label_value_length: 2048
  max_label_names_per_series: 15
  reject_old_samples: true
  reject_old_samples_max_age: 168h   # 7 days
  creation_grace_period: 10m
  unordered_writes: true
```

### ✅ 7. Recommended production `ingester` starting point

```yaml
ingester:
  chunk_idle_period: 30m
  chunk_target_size: 1572864
  chunk_encoding: snappy
  max_chunk_age: 2h
  wal:
    enabled: true
    dir: /loki/wal
    checkpoint_duration: 5m
    flush_on_shutdown: true
```

## 16.3 Simple Scalable Deployment (read/write split) sketch

**Shared file, referenced by both deployments** — only `target` differs:

```yaml
# write-deployment values file sets:
target: write

# read-deployment values file sets:
target: read

# everything else (schema_config, storage_config, common, limits_config,
# memberlist.join_members pointing at BOTH deployments' pods) is identical
# and shared between them.
```

This is the pattern used by Grafana's own Helm charts: one common config,
two Deployments differentiated only by `-target=write` / `-target=read`
(plus separate resource sizing/replica counts), scaling ingestion and
querying independently.

# 17. Glossary — Every Core Term, Defined Once

| Term | Definition |
|---|---|
| **Stream** | The set of all log lines sharing one exact combination of label values. The fundamental unit Loki indexes. |
| **Chunk** | A compressed blob of consecutive log lines for one stream, the fundamental unit Loki stores in object storage. |
| **Label** | An indexed key/value pair attached to a stream (e.g. `job="nginx"`). Low-cardinality by design. |
| **Structured metadata** | Per-line key/value data stored with a chunk but **not** indexed as a label — no cardinality cost. |
| **Cardinality** | The number of unique label-value combinations. High cardinality = more streams = more chunks = slower & pricier Loki. |
| **Ingester** | Component that buffers, chunks, WALs, and flushes incoming log data. |
| **Distributor** | Stateless component that validates and routes incoming writes to ingesters. |
| **Querier** | Component that executes LogQL queries against ingesters + storage. |
| **Query frontend** | Splits/queues/parallelizes/caches queries before handing them to queriers. |
| **Query scheduler** | Optional component that decouples the query queue from the frontend process. |
| **Compactor** | Merges index files and enforces retention/deletion. |
| **Ruler** | Evaluates Prometheus-style recording & alerting rules over log data. |
| **Index gateway** | Serves index lookups without every querier needing direct, constant object-store access. |
| **Bloom filter (bloom-build/-gateway)** | Experimental probabilistic structure to skip chunks that provably can't match a filter query. |
| **Ring** | A consistent-hash structure (backed by a KV store) that lets stateful components (ingesters, compactors...) coordinate ownership of data/work. |
| **WAL (Write-Ahead Log)** | On-disk log of recent writes, replayed on ingester restart to avoid data loss. |
| **Schema config / period config** | A dated timeline of "which index type + which object store + which schema version" applies to logs from a given date onward. |
| **Retention** | How long data is kept before the compactor deletes it. |
| **Tenant (`X-Scope-OrgID`)** | Loki's multi-tenancy identifier; isolates data between organizations/teams sharing one cluster. |
| **Runtime config** | A hot-reloaded YAML file (no restart needed) used mainly for per-tenant limit overrides. |
| **LogQL** | Loki's query language (not covered by this config-focused guide — see Loki's query documentation). |
