# Loki Deployment Modes : Complete Understanding Guide 📊

---

## One-Sentence Answer

**Loki ships as one binary that can run in three different shapes — Monolithic (everything together), Simple Scalable/SSD (split into read/write/backend), or Microservices (every component split apart) — and you pick the shape based on how much log volume you need to handle.**

---

## Analogy Section 🍔

Think of Loki like **running a restaurant kitchen** that can be staffed three different ways.

```
╔══════════════════════════════════════════════════════════════╗
║              🍳 THE LOKI KITCHEN ANALOGY                       ║
║                                                                ║
║  🧑‍🍳 MONOLITHIC = "One Cook Does Everything"                   ║
║     One person preps, cooks, and plates. Fine for a           ║
║     food truck (small volume).                                 ║
║                                                                ║
║  👨‍🍳👩‍🍳 SSD = "Prep Station / Line Station / Back Station"       ║
║     Three teams: one preps orders (write), one plates &        ║
║     serves (read), one handles inventory & cleanup (backend).  ║
║     Good for a busy restaurant (up to ~1TB/day).               ║
║                                                                ║
║  🧑‍🍳🧑‍🍳🧑‍🍳🧑‍🍳🧑‍🍳🧑‍🍳🧑‍🍳 MICROSERVICES = "Full Brigade de Cuisine"    ║
║     Every station has its own specialist chef — grill, sauce,  ║
║     salad, pastry — each scaled independently. For a massive   ║
║     restaurant chain (huge, complex operations).                ║
╚══════════════════════════════════════════════════════════════╝
```

**Process:**
1. Small operation → one cook (Monolithic) handles it all with `-target=all`.
2. Growing operation → split into three stations (SSD): write, read, backend.
3. Huge operation → every dish gets its own specialist chef (Microservices), each independently scalable.

## Complete Data/Process Flow

### STEP 1 — Choosing a Mode via `-target` Flag

```
┌─────────────────────────────────────────────────────────┐
│  🎛️ STEP 1: The -target Flag Controls Everything           │
│                                                            │
│  Same binary, different startup flag:                       │
│    -target=all      → Monolithic mode                        │
│    -target=write    → SSD write path                          │
│    -target=read     → SSD read path                           │
│    -target=backend  → SSD backend path                        │
│    -target=<component> → Microservices (e.g. -target=ingester)│
│                                                            │
│  💡 It's ONE binary/Docker image the whole time — only        │
│     the flag changes which microservices start up             │
└─────────────────────────────────────────────────────────┘
```

### STEP 2 — Monolithic Mode Setup

```
┌─────────────────────────────────────────────────────────┐
│  🧑‍🍳 STEP 2: Monolithic Mode (-target=all)                  │
│                                                            │
│  ALL microservices run in ONE process:                       │
│    Distributor + Ingester + Querier + Query Frontend +       │
│    Compactor + Ruler + Index Gateway + ... (everything)       │
│                                                            │
│  Volume ceiling: ~20GB/day                                    │
│                                                            │
│  Scaling option:                                              │
│    Multiple instances + shared object store +                 │
│    ring section configured in loki.yaml                        │
│                                                            │
│  High Availability recipe:                                      │
│    2 instances + memberlist_config + shared object store       │
│    + replication_factor = 3 + round-robin traffic routing        │
│                                                            │
│  💡 Query parallelization capped by # of instances AND          │
│     max_query_parallelism setting in loki.yaml                   │
└─────────────────────────────────────────────────────────┘
```

### STEP 3 — Simple Scalable Deployment (SSD) Setup

```
┌─────────────────────────────────────────────────────────┐
│  👨‍🍳 STEP 3: SSD Mode — Three Targets                        │
│                                                            │
│  ⚠️ CAUTION: SSD is being DEPRECATED, removed in Loki 4.0     │
│     → migrate to Microservices or HA Monolithic                │
│                                                            │
│  -target=write  (Stateful, K8s StatefulSet)                   │
│    → Distributor + Ingester                                    │
│                                                            │
│  -target=read   (Stateless, K8s Deployment*)                   │
│    → Query Frontend + Querier                                  │
│    (*Helm chart currently deploys it as a StatefulSet)         │
│                                                            │
│  -target=backend (Stateful, K8s StatefulSet)                    │
│    → Compactor + Index Gateway + Query Scheduler + Ruler +      │
│      Bloom Planner + Bloom Builder + Bloom Gateway (all exp.)    │
│                                                            │
│  Volume ceiling: close to 1TB/day                                │
│                                                            │
│  💡 Requires a reverse proxy (Helm chart defaults to Nginx)       │
│     in front, to route client requests to read vs write nodes     │
└─────────────────────────────────────────────────────────┘
```

### STEP 4 — Microservices Mode Setup

```
┌─────────────────────────────────────────────────────────┐
│  🧑‍🍳🧑‍🍳🧑‍🍳 STEP 4: Microservices — Every Component Separate    │
│                                                            │
│  Each of these runs as its OWN distinct process/target       │
│  (release 3.3 list):                                          │
│    Bloom Builder*, Bloom Gateway*, Bloom Planner*,             │
│    Compactor, Distributor, Index Gateway, Ingester,             │
│    Overrides Exporter, Querier, Query Frontend,                  │
│    Query Scheduler, Ruler, Table Manager (deprecated)             │
│    (* = experimental)                                              │
│                                                            │
│  Check your version's full list:                                   │
│    docker run docker.io/grafana/loki:3.7.0                          │
│      -config.file=/etc/loki/local-config.yaml -list-targets           │
│                                                            │
│  💡 Best for VERY large clusters or operators needing precise      │
│     per-component scaling control — but most complex to run          │
└─────────────────────────────────────────────────────────┘
```

### STEP 5 — Switching Modes Later

```
┌─────────────────────────────────────────────────────────┐
│  🔄 STEP 5: Redeploying Under a Different Mode              │
│                                                            │
│  Because Loki DECOUPLES stored data from the software         │
│  that ingests/queries it:                                       │
│                                                            │
│    Monolithic  ⇄  SSD  ⇄  Microservices                          │
│                                                            │
│  → minimal or NO configuration changes needed to switch          │
│    between modes as your needs grow                               │
│                                                            │
│  💡 You're not locked in — start small (Monolithic) and            │
│     graduate to SSD or Microservices later                          │
└─────────────────────────────────────────────────────────┘
```

## Deep Dive Sections

### 🧑‍🍳 Monolithic Mode

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: All Loki microservices in a single process/  │
│              binary/Docker image                            │
│  CONTAINS:   Every component (write + read + backend),      │
│              activated by -target=all                         │
│  WHY IT MATTERS: Fastest way to get started; simplest         │
│    operational model                                            │
│                                                            │
│  Example A: Single instance, no HA                              │
│             → simplest, but no redundancy                         │
│  Example B: 2 instances + memberlist_config + shared object      │
│             store + replication_factor=3 + round-robin routing    │
│             → High Availability setup                              │
│  (Same mode, different config → very different resilience)         │
└───────────────────────────────────────────────────────┘
```

### 👨‍🍳 Simple Scalable Deployment (SSD)

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Middle ground — 3 targets instead of 1 or many │
│              (⚠️ deprecated, removed in Loki 4.0)              │
│  CONTAINS:   write target, read target, backend target         │
│  WHY IT MATTERS: Default mode in the Loki Helm Chart;           │
│    balances simplicity with independent scaling                  │
│                                                            │
│  Example A — Write target:                                        │
│    Components: Distributor, Ingester                                │
│    Type: Stateful (K8s StatefulSet)                                  │
│  Example B — Read target:                                            │
│    Components: Query Frontend, Querier                                │
│    Type: Stateless (K8s Deployment, though Helm currently             │
│           runs it as a StatefulSet)                                     │
│  Example C — Backend target:                                            │
│    Components: Compactor, Index Gateway, Query Scheduler,                │
│                Ruler, Bloom Planner*, Bloom Builder*,                      │
│                Bloom Gateway* (* = experimental)                            │
│    Type: Stateful (K8s StatefulSet)                                          │
│                                                            │
│  (Same overall mode → 3 very different statefulness/scaling         │
│   profiles depending on which target you're looking at)               │
└───────────────────────────────────────────────────────┘
```

### 🧑‍🍳🧑‍🍳🧑‍🍳 Microservices Mode

```
┌───────────────────────────────────────────────────────┐
│  WHAT IT IS: Every component as its own distinct process    │
│              (a.k.a. "Distributed deployment")                 │
│  CONTAINS:   13 separate targets in release 3.3 (see list      │
│              above), each launched individually                  │
│  WHY IT MATTERS: Maximum granularity — scale exactly the        │
│    component under load, nothing else                              │
│                                                            │
│  Example A: High ingest volume, normal query load                    │
│             → scale ONLY Distributor + Ingester replicas               │
│  Example B: Low ingest volume, heavy query load                        │
│             → scale ONLY Querier + Query Frontend replicas               │
│  (Same cluster, different bottleneck → scale only what's needed,         │
│   impossible to do this precisely in Monolithic or SSD)                    │
└───────────────────────────────────────────────────────┘
```

## Full Lifecycle Diagram

```
1️⃣  Start with Loki binary — decide deployment mode via -target flag
        ▼
2️⃣  🧑‍🍳 SMALL SCALE (≤20GB/day): -target=all → Monolithic mode
       (optionally add HA: 2 instances + shared object store +
        memberlist_config + replication_factor=3)
        ▼
3️⃣  📈 Volume grows past small scale → migrate (minimal config
       change, since storage is decoupled from compute)
        ▼
4️⃣  👨‍🍳 MEDIUM-LARGE SCALE (up to ~1TB/day): SSD mode
       -target=write  → Distributor + Ingester (stateful)
       -target=read   → Query Frontend + Querier (stateless)
       -target=backend → Compactor + Index Gateway + Query
                         Scheduler + Ruler + Bloom trio (stateful)
       + reverse proxy (e.g. Nginx) routes read vs write traffic
        ▼
5️⃣  ⚠️ SSD is being deprecated (removed in Loki 4.0)
        ▼
6️⃣  📈 Volume grows further OR need precise per-component control
       → migrate to Microservices mode
        ▼
7️⃣  🧑‍🍳🧑‍🍳🧑‍🍳 VERY LARGE SCALE: Microservices mode — each of
       13 components runs & scales as its own process
       (Distributor, Ingester, Querier, Query Frontend, Query
        Scheduler, Compactor, Index Gateway, Ruler, Overrides
        Exporter, Bloom Planner/Builder/Gateway, Table Manager)
```

## Key Takeaways

**Core mechanics:**
- ✅ Loki is **one binary**; the `-target` flag decides which microservices actually start.
- ✅ Storage is **decoupled** from compute → switching modes later needs minimal/no config changes.

**Choosing a mode:**
- ✅ **Monolithic** (`-target=all`) — simplest, good up to ~20GB/day, can add HA with replication_factor=3.
- ✅ **SSD** (`write`/`read`/`backend`) — balances simplicity and scale up to ~1TB/day, but is **being deprecated** (gone in Loki 4.0).
- ✅ **Microservices** — every component its own process, most scalable and most complex, designed for Kubernetes.

**Operational notes:**
- ✅ SSD's write and backend targets are **stateful** (StatefulSet); its read target is meant to be **stateless**.
- ✅ SSD requires a **reverse proxy** (Nginx by default in the Helm chart) to route read vs. write traffic.
- ✅ Use `-list-targets` to see the exact component list for your Loki version.

**One-line flow:**
`Pick -target flag → Monolithic (small) → SSD (medium, deprecated) → Microservices (large) — same data, swap modes anytime`

## Memory Trick 🧠

> **"All, Write/Read/Backend, or Every-One-Alone."**
> - **M**onolithic = **A**LL in one (`-target=all`)
> - **S**SD = **3** groups (Write, Read, Backend)
> - **M**icroservices = **13+** solo components
>
> Think of it as **1 → 3 → Many** — the number of independently-scalable pieces grows as your log volume grows.

## Plain-Language Summary

The original Grafana Loki documentation explains that Loki is built as a single binary containing all of its microservices, and the `-target` command-line flag controls which of those microservices actually run. There are three deployment shapes: **Monolithic mode** (`-target=all`) runs everything in one process, is the simplest way to get started, and suits small workloads (~20GB/day), with optional high-availability configuration using replication and a shared object store. **Simple Scalable Deployment (SSD)** splits Loki into three targets — write (Distributor + Ingester, stateful), read (Query Frontend + Querier, stateless), and backend (Compactor, Index Gateway, Query Scheduler, Ruler, and the experimental Bloom components, stateful) — scaling to nearly 1TB/day, though it's being deprecated and removed in Loki 4.0. **Microservices mode** runs every individual component (13+ in release 3.3) as its own separate process for maximum scaling precision, at the cost of operational complexity, and is intended for very large, Kubernetes-based deployments. Because Loki decouples stored data from the software that reads/writes it, operators can migrate between these modes later with minimal configuration changes as their log volume grows.
